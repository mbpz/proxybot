## 3. P0 — Per-host TLS decryption rules

### 3.1 Problem

Today ProxyBot MITMs every HTTPS connection in its capture path. Two
classes of mobile app immediately break the proxy:

- **Certificate-pinned apps** (WeChat 8.0+, Alipay, most banking apps)
  — connection fails outright, app exits.
- **Telemetry / analytics** (Firebase, Bugly, Sensors, advertising SDKs)
  — flood the capture with noise that drowns out the app's own API.

User workarounds today: edit `~/.proxybot/rules.yaml` to add
`Direct` entries, restart the proxy. Painful for non-developers.

### 3.2 Design

Add a new Tauri-managed table `tls_decryption_rules` keyed on
**hostname glob pattern** with three actions:

```
{ pattern: "*.weixin.qq.com", action: "Bypass" }
{ pattern: "*.bugly.qq.com",  action: "Bypass" }
{ pattern: "api.example.com", action: "Decrypt" }
{ pattern: "*.example.com",   action: "Passthrough" }
```

Action semantics in `cert_manager.rs`:

- `Bypass` — `cert_manager` issues no leaf; CONNECT tunnel goes
  straight through, request is not decrypted. Captures only the
  CONNECT metadata (host, bytes_in, bytes_out).
- `Passthrough` — like Bypass but no capture at all (for high-volume
  hosts the user genuinely doesn't want to see).
- `Decrypt` — current behaviour, MITM with leaf cert. Default when
  no rule matches.

Pattern matching reuses the existing `glob_match` from
`proxybot_core::fingerprint`.

### 3.3 UI

- `Certs` tab gains a "Decryption rules" sub-panel.
- List view: pattern + action badge + hit count (from a
  per-host counter in `db`).
- "+ Add rule" modal: pattern textbox + action dropdown.
- Wildcard hint placeholder (`*.example.com`).

### 3.4 Files touched

- `proxybot-core/src/cert_manager.rs` — accept per-host decision
  based on the rule list.
- `src-tauri/src/db.rs` — migration v6 adds `tls_decryption_rules`
  table.
- `src-tauri/src/commands/cert.rs` — CRUD commands.
- `src/components/cert/DecryptionRules.tsx` — new sub-panel.

### 3.5 Acceptance

- Mobile capture session: WeChat traffic appears as `Bypass`
  (metadata-only), app's own API still decrypts cleanly.
- Adding `*.bugly.qq.com` + `Bypass` removes Bugly noise from the
  request list without restart.
- Tests: `cert_manager` rule-lookup unit tests cover wildcard +
  exact + no-match-default-to-decrypt paths.

## 4. P0 — Interactive request interception (breakpoints)

### 4.1 Problem

ProxyBot today has YAML rules that can `MapLocal` / `MapRemote` /
`Respond` but they're static. The fundamental debugging loop —
"this request failed, let me change the header and replay" — needs
interactive edit-and-forward, not a file save + proxy restart.

Proxelar's `pause` action, mitmproxy's `@response.terminate`,
Charles's "Breakpoints" tab, Rockxy's "Breakpoint" tool — all
established UX.

### 4.2 Design

There is already partial infrastructure:
- `state_machine.rs` exposes `BreakpointDecision` enum
- `proxy/mod.rs` has `breakpoint_tx` channel
- `commands/specgen.rs` referenced a `BreakpointRequest` (untouched since)

What's missing is the bridge to the user. Design:

1. **Trigger rules** — extend `RuleAction` with `Breakpoint`. When a
   request matches a `Breakpoint` rule, send a `BreakpointRequest`
   to `breakpoint_tx` and suspend the connection until a
   `BreakpointDecision` arrives.
2. **Bridge** — new `breakpoint/mod.rs` listener reads
   `breakpoint_tx`, writes to a bounded `VecDeque<PendingBreakpoint>`
   inside `AppState`, emits `breakpoint:new` Tauri event to the
   frontend, waits on a `tokio::sync::oneshot` paired with each
   pending id.
3. **UI** — a docked panel (`BreakpointPanel.tsx`) shows pending
   breakpoints with method / host / path / headers / body. User
   picks:
   - **Forward as-is** (send decision `Continue`)
   - **Edit and forward** (mutate `BreakpointRequest`, then
     `Continue`)
   - **Drop** (`Abort`)
   - **Respond locally** (return a stub `BreakpointDecision::Respond`)
4. **Cleanup** — on app shutdown, all pending breakpoints resolve
   to `Continue` to avoid stranding connections.

### 4.3 Files touched

- `src-tauri/src/rules.rs` — `RuleAction::Breakpoint { method, url }`
  variant.
- `src-tauri/src/state_machine.rs` — wire breakpoint channel into
  the rule pipeline.
- `src-tauri/src/breakpoint/mod.rs` — new module.
- `src-tauri/src/lib.rs` — register, emit event.
- `src/components/breakpoint/BreakpointPanel.tsx` — new panel.
- `proxybot-core/src/types.rs` — `BreakpointDecision` already exists
  in current state, may need a `Mutated` variant for edit-and-forward.

### 4.4 Acceptance

- User adds a YAML rule:
  ```yaml
  - { method: POST, pattern: /api/checkout, action: Breakpoint }
  ```
- App sends POST /api/checkout — request suspends; the Breakpoint
  panel pops up showing the pending request.
- User edits the JSON body, clicks Forward; the modified body
  goes upstream and the response comes back.
- Tests: state_machine handles `Breakpoint` action → emits event;
  mock event handler returns `Mutated` decision → pipeline resumes
  with mutated body.

## 5. P1 — Compressed body decode

### 5.1 Problem

`commands/specgen.rs::decode_body` already handles binary → fallback
to `[binary N bytes]`. But if `Content-Encoding: gzip` is on the
response, the captured body is gzipped bytes — even valid UTF-8
JSON gets misclassified as binary.

`har.rs::HarContent` similarly stores `text` as the raw bytes.

### 5.2 Design

Add a single helper `proxybot-core::body::decompress(bytes,
content_encoding) -> Result<Vec<u8>, Error>` that handles gzip /
brotli / deflate. Wire it into two places:

1. **`specgen::decode_body`** in `commands/specgen.rs` — if decode
   succeeds and the result is valid UTF-8, return as String;
   otherwise fall back to `[binary N bytes]` placeholder.
2. **`HarContent.text`** in `har.rs` — decode before assignment.

Brotli needs the `brotli` crate (already a transitive dep via
reqwest). Re-export; do not add to public API.

### 5.3 Files touched

- `proxybot-core/src/body.rs` — new module with `decompress`.
- `proxybot-core/src/lib.rs` — re-export.
- `src-tauri/src/commands/specgen.rs` — call decompress first.
- `src-tauri/src/har.rs` — same.

### 5.4 Acceptance

- Capture a `GET /api/data` where upstream returns
  `Content-Encoding: gzip`. The traffic list shows the JSON, not
  `[binary 1234 bytes]`.
- HAR export contains decoded `text` field, not raw gzipped bytes.
- Tests: decompress round-trips gzip/brotli/deflate samples; invalid
  data returns Err (falls back to binary marker).

## 6. P1 — Reverse proxy mode + body modification hooks

### 6.1 Problem

Proxelar's `-m reverse --target http://localhost:3000` puts the
proxy in front of a local service for mock-style testing. Today
ProxyBot can only do this indirectly via `MapRemote` rules that
forward to localhost — workable but verbose.

### 6.2 Design

Two related pieces:

#### 6.2.1 Reverse proxy mode

A new top-level config key:

```toml
[reverse]
enabled = true
target = "http://localhost:3000"
```

When enabled, the proxy binds the regular port but routes every
unmatched request to `target` instead of doing DNS lookup +
forward. Useful for frontend devs who want to inject a local
backend without editing `rules.yaml`.

CLI flag: `--reverse --target http://localhost:3000` for one-shot
testing.

#### 6.2.2 Body modification hooks

Currently `Rhai` scripts expose `block` but no body rewrite. Add
two new script functions:

```rust
// in scripting/engine.rs:
register_fn("rewrite_request_body", |ctx: &mut mut Request, new_body: String| { ... });
register_fn("rewrite_response_body", |ctx: &mut mut Response, new_body: String| { ... });
```

This is a tiny extension to the existing scripting module and
gives users the same power as Proxelar's Lua rewrite scripts
without introducing a new scripting language.

### 6.3 Files touched

- `proxybot-core/src/config.rs` — add `ReverseConfig`.
- `src-tauri/src/proxy/listener.rs` — branch on reverse mode.
- `src-tauri/src/scripting/engine.rs` — add two `register_fn`s.
- `src/components/settings/ReverseProxy.tsx` — small settings panel.

### 6.4 Acceptance

- Run `proxybot --reverse --target http://localhost:3000`. App
  configures browser to point at ProxyBot; requests land on the
  local backend.
- Rhai script `rewrite_response_body(req, resp, newBody)` replaces
  the response body before forwarding to the client. Test with
  mock data script in `examples/`.

## 7. Out of scope for v1.3

- **Process-level attribution** (G-6) — needs macOS-specific
  `proc_pid` / `so_procinfo` integration; defer to v1.4 with a
  dedicated spike.
- **PCAP export** (G-7) — HAR covers the 95% case; revisit if a
  user files the feature.
- **WebSocket Protobuf decode** (G-8) — niche.
- **Saved filters + full-text search** (G-5) — useful but not
  parity-blocking. v1.4 candidate.

## 8. Rollout plan

1. **G-1 Per-host TLS rules** — independent; ship first. Touches
   `cert_manager`, a new DB migration, a new UI panel. ~5-7 days.
2. **G-3 Decompress** — small, unblocks the other work because
   breakpoints will display decoded bodies correctly. ~1 day.
   Land immediately after G-1.
3. **G-2 Breakpoints** — largest single feature. Depends on
   `BreakpointRequest` plumbing that already exists. ~7-10 days.
4. **G-4 Reverse proxy + body hooks** — small once the other
   three land. ~2-3 days.

Total: ~3-4 weeks with one engineer; can parallelise G-1/G-3
against G-2 since they touch different modules.
