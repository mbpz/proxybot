# P4.3-A device identity isolation prototype

## Config model

`minimal/examples/devices.json`:

```json
{
  "devices": [
    {"device_key":"device-a","source_ip_cidr":"192.168.3.190/32","client_ip":"192.168.3.190"},
    {"device_key":"device-b","source_ip_cidr":"192.168.3.191/32","client_ip":"192.168.3.191"}
  ]
}
```

Generator invariants (unit-tested):

- device keys unique and safe for outbound tags;
- source CIDRs IPv4, unique and non-overlapping;
- each `client_ip` lies inside its `source_ip_cidr`;
- client IPs unique;
- per-device TCP/443 rules appear before the generic `mitm` rule;
- unregistered sources fall through to generic `mitm` with no client-ip
  metadata, so they are recorded as `unknown`, not as a registered device.

Generated config:

```text
outbounds: mitm, proxybot-device-device-a, proxybot-device-device-b, direct
rules[1]: tcp 443 source 192.168.3.190/32 -> proxybot-device-device-a
rules[2]: tcp 443 source 192.168.3.191/32 -> proxybot-device-device-b
rules[3]: tcp 80 -> transparent adapter (unknown identity)
rules[4]: tcp 443 -> generic mitm (unknown identity)
```

`singbox-config --devices ...` and `gateway start --devices ...` run the same
validator; the supervisor additionally runs `sing-box check` before spawning.

## Current evidence

- `cargo test`: 5 passed (includes overlap/duplicate/client-outside-CIDR rejection
  and rule ordering).
- generated JSON passes `sing-box check`.
- phone P4.2 path already proves static metadata reaches Hudsucker and is stored.

## Dual-device test evidence (2026-10-26)

Config: `gateway start --devices minimal/examples/devices.json`.

Observed in the same window:

```text
192.168.3.190  https  37 requests  identity_source=tun_source_ip confidence=inferred
192.168.3.191  https 168 requests  identity_source=tun_source_ip confidence=inferred
unregistered   http   10 requests  identity_source=unknown confidence=unknown
```

- A and B were active concurrently and their `client_ip` values did not cross.
- `example.com` HTTPS rows from B were assigned to B; unknown-source HTTP/80
  rows remained unknown.
- HTTP/80 from all sources remained `client_ip=NULL`, `identity_source=unknown`.
- `connection_id` remained proxy-side (`127.0.0.1:<port>`), as documented.

Still to verify explicitly: A and B concurrently opening the **same HTTPS domain**
at the exact same time; the current sample has same-domain traffic mostly from B.
The routing rule is per source CIDR, so this should be independent, but it needs
the explicit acceptance observation.

## Test procedure

Two devices on the same LAN:

- A: `192.168.3.190`
- B: `192.168.3.191` (choose an actually free address)

```bash
proxybot start
sudo proxybot gateway start --devices minimal/examples/devices.json
```

Then:

1. A only visits HTTPS; assert `client_ip=192.168.3.190`.
2. B only visits HTTPS; assert `client_ip=192.168.3.191`.
3. A and B concurrently visit the same domain; assert no cross-assignment.
4. A and B concurrently visit different domains.
5. A opens several sequential connections; all stay A.
6. An unregistered source (e.g. `192.168.3.189`) visits HTTPS; assert
   `client_ip=NULL`, `identity_source=unknown`, `confidence=unknown`.
7. HTTP/80 remains unknown.
8. Gateway stop/restore regression.

## Boundary

- `confidence=inferred`: static per-device metadata proves config mapping, not a
  per-connection ingress observation.
- `connection_id` remains proxy-side loopback; full TUN ingress connection
  correlation is P4.3-B.
- Static metadata cannot distinguish two devices sharing one source CIDR; the
  validator rejects overlap.
