# P4.2 single-device metadata prototype

## What was verified

sing-box 1.14.4 **does** carry custom headers on the HTTP `CONNECT` request.
A controlled loopback proxy captured a real CONNECT from sing-box:

```text
CONNECT example.com:80 HTTP/1.1
Host: example.com:80
Proxy-Connection: Keep-Alive
X-Proxybot-Client-Ip: 192.168.3.190
X-Proxybot-Confidence: confirmed
X-Proxybot-Connection-Id: conn-test-1
X-Proxybot-Identity-Source: tun_source_ip
X-Proxybot-Source: gateway
```

Header names are canonicalized (`Client-Ip`), values are preserved. Configuration
is not enough by itself; this raw CONNECT capture was used as evidence.

## Implemented

- `proxybot singbox-config --client-ip <IP>` and
  `proxybot gateway start --client-ip <IP>` add:
  - `X-ProxyBot-Source: gateway`
  - `X-ProxyBot-Client-IP: <IP>`
  - `X-ProxyBot-Identity-Source: tun_source_ip`
  - `X-ProxyBot-Confidence: inferred`
- ProxyBot accepts metadata only on a loopback `CONNECT` with
  `X-ProxyBot-Source: gateway`.
- All `X-ProxyBot-*` headers are stripped before forwarding.
- `client_ip`, `peer_ip`, `connection_id`, `identity_source`, `confidence` are
  persisted with an additive SQLite migration.
- `device_id` remains `NULL`; no stable device registration exists yet.
- `connection_id` currently falls back to the loopback proxy connection
  (`127.0.0.1:<port>`), not the original TUN ingress connection.
- HTTP/80 through the transparent adapter remains `identity_source=unknown`,
  `confidence=unknown`.

Local loopback test result:

```text
source_type=gateway
client_ip=192.168.3.190
peer_ip=127.0.0.1
device_id=NULL
connection_id=127.0.0.1:62201
identity_source=tun_source_ip
confidence=inferred
host=example.com
```

## Trust boundary

- LAN clients cannot establish identity metadata: the connection must be
  loopback and carry the gateway source marker.
- External `X-ProxyBot-*` headers are removed before forwarding.
- A local process can still connect over loopback and spoof metadata. Stronger
  process authentication (token/HMAC or Unix-socket ownership) is deferred.
- `importance`: the static per-device header is an `inferred` identity; it proves
  the configured route mapping, not per-connection ingress observation.
  `confirmed` is reserved for the adapter that carries a real ingress
  connection id.

## Phone validation: PASSED

iPhone HTTPS `example.com` after `gateway start --client-ip 192.168.3.190`:

```text
source_type=gateway
scheme=https
host=example.com
client_ip=192.168.3.190
peer_ip=127.0.0.1
device_id=NULL
connection_id=127.0.0.1:62727
identity_source=tun_source_ip
confidence=inferred
```

HTTP/80 requests from the same phone remained:

```text
source_type=gateway
identity_source=unknown
confidence=unknown
client_ip=NULL
```

Known gap: `connection_id` is the proxy-side loopback connection, not the TUN
ingress connection, so this prototype does not yet satisfy full ingress-to-
request association. `confidence=inferred` reflects that limitation.

## Original test procedure

```bash
proxybot start
sudo proxybot gateway start --client-ip 192.168.3.190
# iPhone HTTPS request
curl -s 'http://127.0.0.1:8899/api/requests?limit=1' | jq '.[0] | {client_ip,peer_ip,device_id,connection_id,identity_source,confidence}'
sudo proxybot gateway stop
```

Expected: `client_ip=192.168.3.190`, `peer_ip=127.0.0.1`, `device_id=null`,
`identity_source=tun_source_ip`, `confidence=inferred`; HTTP/80 stays unknown.
